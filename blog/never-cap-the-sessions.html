Never cap the sessions

Sessions 永遠唔封頂

Sessions 永遠不設上限

Sessions 永远不设上限

People see this screenshot and ask how I keep track of it all. Honest answer: I don't track the windows. I track the board.

I am one person. I don't write most of the code anymore. I decide what gets built, I correct course, I approve what ships. The sessions do the rest — in parallel, all the time. In the last 30 days my coding agent alone ran 2,181 sessions. Not 2,181 prompts. Sessions.

“Running that many AIs must be hard”

It is. I said exactly that today, looking at this screen. Every session eventually comes back with a question, a decision, a “your turn.” A dozen sessions means a dozen queues, all of them pointing at one human.

But here is the thing nobody gets: the hard part is not the number of sessions. The hard part would be shipping all of this with three.

Active sessions are never capped. That is the source of my productivity.

A cap sounds like discipline. It is not. A cap is a queue of work that hasn't started, ideas going stale while they wait for a slot. My bottleneck was never ideas, and it was never code. It was one pair of hands. The sessions removed the hands from the equation. Capping them puts the hands back.

The board is the single pane

What makes unlimited parallel manageable is not a bigger screen. It is a contract. Every session I spawn works in its own worktree and ends with exactly one of two lines:

AGENT-BOARD: DONE — what shipped, and how it was verified.
AGENT-BOARD: BLOCKED — what is missing, and what it needs from me.

The agent board collects those reports into one pane. I read reports, not terminals. The wall of windows sits behind the board, and I almost never look at it directly — except on evenings like this one, when I screenshot it because, honestly, it looks iconic.

The machine pays for it. Good.

None of this is free, and the Activity Monitor does not lie about it:

People look at numbers like that and suggest closing some sessions to “give the machine a break.” That is solving the wrong problem. RAM is a hardware problem — the fix is more RAM. Quota is a plan problem — the fix is a bigger plan. Sessions are the product. You do not fix a factory by switching off machines.

The rule going forward

So the wall stays. It will probably get bigger. One architect, one board, as many sessions as the work needs.

Cap the meetings. Cap the context switches. Never cap the sessions.

人哋見到呢張截圖，就問我點樣跟得晒。老實答：我唔係跟 window，我跟嘅係 board。

我得一個人。我已經唔再寫大部分 code。我決定起咩、我修正方向、我批准出貨。Sessions 做埋其餘嘅嘢 — 並行咁做，冇停過。過去 30 日，淨係我個 coding agent 就行咗 2,181 個 sessions。唔係 2,181 個 prompts，係 sessions。

「同時行咁多 AI 一定好難」

係難。我今日望住呢個畫面，講嘅正正就係呢句。每個 session 到最後都會返嚟，帶住一個問題、一個決定、一句「到你啦」。十幾個 sessions，就係十幾條 queue，全部指向同一個人。

但冇人明嘅係：難嘅唔係 sessions 嘅數量。難嘅係要用三個 sessions，出晒呢度全部貨。

Active sessions 永遠唔封頂。呢個就係我生產力嘅來源。

封頂聽落好似紀律，其實唔係。封頂只係一條未開工嘅 queue，啲諗法等緊個位，等到過期。我嘅 bottleneck 從來唔係諗法，亦唔係 code，係得一對手。Sessions 將雙手移出咗成條方程式。封頂佢哋，就係將雙手放返入去。

Board 就係嗰塊總覽板

等無限並行變得管理得到嘅，唔係一塊更大嘅螢幕，係一份合約。我開嘅每個 session 都喺自己嘅 worktree 入面做嘢，最後只會交返兩句說話其中一句：

AGENT-BOARD: DONE — 出咗咩貨，點樣驗證。
AGENT-BOARD: BLOCKED — 爭啲咩，需要我畀啲咩。

Agent board 將呢啲報告收埋入同一塊板。我睇報告，唔睇 terminal。嗰牆 window 喺 board 後面，我幾乎唔會直接望佢 — 除咗好似今晚咁，截低佢，因為老實講，個畫面真係好 iconic。

部機要埋單。好，應該嘅。

呢一切都唔係免費，Activity Monitor 唔會講大話：

人哋見到啲咁嘅數字，就會提議閂咗啲 sessions，等部機「抖下」。咁係解決錯咗個問題。RAM 係硬件問題 — 解法係加 RAM。Quota 係 plan 問題 — 解法係升 plan。Sessions 先係產品。你唔會閂工廠啲機嚟修間工廠。

以後嘅規則

所以嗰牆會留低。好可能仲會越嚟越大。一個 architect、一塊 board，工作需要幾多 sessions 就開幾多。

Meetings 可以封頂。Context switches 可以封頂。Sessions，永遠唔封頂。

人們看到這張截圖，就問我如何追蹤這一切。誠實的答案是：我不追蹤視窗。我追蹤的是 board。

我只有一個人。我已經不再親自撰寫大部分的程式碼。我決定要打造什麼、修正方向、核准出貨的內容。其餘的事由 sessions 完成——平行進行、無時無刻。在過去 30 天，光是我的 coding agent 就跑了 2,181 個 sessions。不是 2,181 個 prompts。是 sessions。

「同時跑這麼多 AI 一定很難」

確實很難。今天看著這個畫面，我說的正是這句話。每個 session 最後都會回來，帶著一個問題、一個決定、一句「輪到你了」。十幾個 sessions，就代表十幾條佇列，全部指向同一個人。

但沒人理解的是：困難的部分不是 sessions 的數量。困難的部分，是只用三個 sessions 把這一切全部出貨。

進行中的 sessions 永遠不設上限。這是我生產力的來源。

設上限聽起來像紀律。其實不是。上限是一條尚未開始的工作佇列，是那些想法在等待空位時逐漸過期。我的瓶頸從來不是想法，也從來不是程式碼。是只有一雙手。Sessions 把雙手從方程式中移除了。給它們設上限，就是把雙手放回去。

Board 就是那塊單一面板

讓無限平行運作變得可管理的，不是一塊更大的螢幕。是一份約定。我啟動的每個 session 都在自己的 worktree 中工作，並以兩行文字的其中一行作結：

AGENT-BOARD: DONE — 出了什麼貨，以及它如何被驗證。
AGENT-BOARD: BLOCKED — 缺少什麼，以及它需要我提供什麼。

Agent board 把這些報告彙整到同一塊面板。我讀的是報告，不是終端機。那面視窗牆就位於 board 後方，我幾乎從不直接看它——除了像今晚這樣的夜晚，我會把它截圖下來，因為老實說，那畫面實在太經典了。

機器為此付出代價。很好。

這一切都不是免費的，而 Activity Monitor 不會說謊：

人們看到這樣的數字，就會建議關掉一些 sessions，讓機器「喘口氣」。那是解決錯了問題。RAM 是硬體問題——解法是更多 RAM。配額是方案問題——解法是更大的方案。Sessions 才是產品。你不會靠關掉機器來修理工廠。

今後的規則

所以那面牆會留下來。它很可能還會變得更大。一位架構師、一塊 board、工作需要多少 sessions 就用多少。

會議可以設上限。上下文切換可以設上限。Sessions，永遠不設上限。

AGENT-BOARD: DONE — 出了什么货，以及它如何被验证。

Agent board 把这些报告汇整到同一块面板。我读的是报告，不是终端机。那面视窗墙就位于 board 后方，我几乎从不直接看它——除了像今晚这样的夜晚，我会把它截图下来，因为老实说，那画面实在太经典了。

今后的规则

所以那面墙会留下来。它很可能还会变得更大。一位架构师、一块 board、工作需要多少 sessions 就用多少。

会议可以设上限。上下文切换可以设上限。Sessions，永远不设上限。
